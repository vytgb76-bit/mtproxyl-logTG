# MTProxyL v1.6.x / Telemt — ежедневные логи в один Telegram-бот

## Что делает

- Предназначено для **MTProxyL LiafanX**, движок **Telemt (бинарник)**, работающий как systemd-служба.
- На каждом VPS запускается одинаковый установщик. Вводятся **разные имена серверов**, но **одинаковые** Telegram bot token и chat_id.
- В **00:00 по локальному времени VPS** (systemd timer) выбирает сообщения службы за **предыдущие сутки**, архивирует и отправляет в чат Telegram.
- Пример: `VPS_NL_2026-10-31.log.gz`, `VPS_DE_2026-10-31.log.gz`.
- После успешной отправки документ удаляется **из собственного каталога отправщика**.
- Если Telegram не ответил, архив хранится до следующей попытки (раз в час).
- Архивы больше ~45 МиБ делятся на несколько файлов `.part...`. Части одной большой gzip-архивной копии нужно соединять в порядке индексов, чтобы распаковать.
- Проверка отправки с помощью команды `test`. Для отправки применяет Bot API `sendDocument`; **не обращается к `getUpdates`**, поэтому не мешает работающему боту MTProxyL.
- Не изменяет сетевые настройки, порт 443, секреты, фильтры, правила MEKO/Zapret2 и **не перезапускает** Telemt.

**Честное ограничение:** исходные записи продолжают находиться в **systemd-journald** (и могут сохраняться там после отправки), поскольку именно оттуда MTProxyL показывает «Потоковые логи». Скрипт **не очищает чужие журналы**, чтобы не удалять записи других служб и не ломать просмотр логов MTProxyL. Поэтому цель «вообще не хранить логи на сервере» требует отдельного изменения архитектуры записи Telemt (например, вывод только в контролируемый файл), при котором может перестать работать пункт «Потоковые логи» MTProxyL. В этой безопасной версии удаляются только созданные отправщиком временные архивы после подтверждённой отправки. Также сохраняются небольшие файлы настроек и состояния; у самого MTProxyL может быть отдельная история IP.

## Установка на каждый VPS

Перед установкой начните чат с выбранным Telegram-ботом и убедитесь, что знаете числовой `chat_id`. Уже существующий бот MTProxyL можно использовать, если он доступен в этом чате и его токен известен. **Никому не присылайте токен, включая в переписку здесь.**

```bash
unzip mtproxyl_multiserver_logbot.zip
cd mtproxyl_multiserver_logbot
sudo bash install.sh
```

Установщик попросит:

1. Имя VPS: `VPS_NL` на одном сервере, `VPS_DE` на другом; разрешены только буквы латиницы, цифры, `_` и `-`.
2. Тот же токен Telegram-бота для обоих VPS.
3. Тот же числовой `chat_id` для обоих VPS.

Он обнаруживает фактическую службу MTProxyL из `mtproxyl mode --json` (или из `settings.conf` для старых установок), проверяет, что она активна, и создаёт **только свои** файлы:

- `/etc/mtproxyl-logship.json` — настройки с токеном, права `0600`;
- `/opt/mtproxyl-logship/logship.py` — скрипт отправки;
- `/var/lib/mtproxyl-logship/` — состояние и ожидающие архивы, права `0700`;
- `/etc/systemd/system/mtproxyl-logship.service` и `.timer`.

**Первую архивируемую дату** установщик задаёт как текущую локальную дату, чтобы следующий запуск в 00:00 забрал весь день установки. Исторические записи до этой даты не отправляются автоматически.

## Включить подробные события подключений

MTProxyL генерирует конфигурацию Telemt, поэтому **не правьте напрямую** `/opt/mtproxyl/mtproxy/telemt.toml` в обычном режиме Manager: менеджер может переписать изменения.

```bash
sudo mtproxyl tune get log_level
sudo mtproxyl tune set log_level verbose
```

При запросе MTProxyL подтвердите перезапуск движка для применения настройки. **Перезапуск временно прервёт активные соединения.** На `silent` подробных соединений может не быть. После изменения подключитесь к прокси с клиента и посмотрите:

```bash
sudo mtproxyl logs
```

Для режима «Супер эксперт» CLI `tune` может быть отключён; тогда настройка меняется через управляемый MTProxyL пользовательский TOML-конфиг, а не установщик логов.

## Проверки и управление

Пробная отправка небольшого файла **без секретов и логов пользователей**:

```bash
sudo python3 /opt/mtproxyl-logship/logship.py test
```

Статус:

```bash
sudo python3 /opt/mtproxyl-logship/logship.py status
systemctl list-timers mtproxyl-logship.timer
```

Немедленно экспортировать все **завершённые сутки**, которые ещё не отправлялись (не отправляет неполные текущие сутки):

```bash
sudo systemctl start mtproxyl-logship.service
sudo journalctl -u mtproxyl-logship.service -n 30 --no-pager
```

Проверить часы VPS:

```bash
timedatectl
```

**Важно:** таймер работает в часовом поясе каждого VPS. Если два сервера расположены в разных часовых поясах, их 00:00 наступит в разные моменты. Для единого 00:00 настроить один и тот же часовой пояс VPS либо дополнительно изменить таймер.

Для отключения:

```bash
sudo bash uninstall.sh
```

Он оставляет ожидающие архивы и токен (во избежание случайной потери), сообщая команды их отдельного удаления. Он не трогает MTProxyL и Telemt.

## Ограничения

- Схема рассчитана на бинарный режим. Для Docker-журналов требуется другой источник (`docker logs`).
- Если MTProxyL переименовал службу движка, обновите поле `unit` в `/etc/mtproxyl-logship.json` на новое имя. Иначе новые записи могут не попадать в отправку.
- Журналы должны быть доступны `journalctl` на момент экспорта; если journald ограничен по размеру или удаляет сообщения раньше следующей полуночи, часть данных может быть утрачена.
- Если клиент использует **один секрет на всех**, лог не определит индивидуальный Telegram-аккаунт. IP и имя секрета — не идентификатор личности.
- Telegram при редком сетевом сбое может получить документ, но отправщик не получить подтверждение; тогда при повторной попытке возможен дубликат этой части.
- Логи могут содержать персональные IP-адреса и сведения о подключениях. Используйте приватный чат, не пересылайте их посторонним и храните не дольше, чем нужно.
