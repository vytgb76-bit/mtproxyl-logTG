# MTProxyL → Telegram: ежедневная отправка логов с нескольких VPS

**mtproxyl-logTG** — дополнительный сборщик журналов для [MTProxyL от LiafanX](https://github.com/Liafanx/MTProxyL) с движком **Telemt**, установленным как **бинарник / systemd-служба**.

Программа отправляет журналы подключений и другие сообщения службы Telemt в **один Telegram-чат через одного бота**. На каждом VPS задаётся собственное имя сервера, чтобы архивы не путались.

> [!IMPORTANT]
> **Проект не удаляет исходные логи Telemt из `systemd-journald`.** После успешной доставки он удаляет только **свои временные архивы**. Если требуется совсем не хранить исходные журналы на VPS, одной установки этого проекта недостаточно. Подробности — в разделе [«Хранение и удаление логов»](#хранение-и-удаление-логов).

## Возможности

- **Один бот для любого количества VPS.** Для всех установок можно использовать одинаковые `bot_token` и `chat_id`.
- **Разные названия архивов:** `VPS_NL_2026-10-31.log.gz`, `VPS_DE_2026-10-31.log.gz` и т. п.
- **Суточный экспорт:** берёт сообщения Telemt из `journalctl` за предыдущий календарный день.
- **Автоматическая отправка:** запуск в начале каждого часа, в том числе в **00:00 по местному времени VPS**. При первом запуске после полуночи архивируются завершившиеся сутки.
- **Повторные попытки:** если Telegram недоступен, неподтверждённые архивы остаются в очереди и отправляются при следующих почасовых запусках.
- **Проверка без пользовательских логов:** команда `test` отправляет небольшой тестовый файл.
- **Отправка больших файлов:** архив делится на части до 45 МиБ, если не помещается в один документ.
- **Без отдельного входящего сервера:** используется запрос `sendDocument` к Telegram Bot API; открывать дополнительные входящие порты не требуется.
- **Без вмешательства в прокси:** установщик не меняет порт 443, секреты, маршрутизацию, MEKO/Zapret2, конфигурацию Telemt и не перезапускает его.

Схема:

```text
VPS_NL (MTProxyL + Telemt) ──┐
                             ├──> один Telegram-бот ──> один приватный чат
VPS_DE (MTProxyL + Telemt) ──┘      с архивами по дням и серверам
```

> [!NOTE]
> Это **отправщик файлов в Telegram**, а не отдельный Telegram-бот с меню и командами. Он может использовать токен уже работающего бота MTProxyL, поскольку **не вызывает `getUpdates`** и не конкурирует за входящие обновления.

## Требования

- Уже установлен и работает **MTProxyL** (в частности, подходит связка MTProxyL v1.6.x + Telemt v3.5.x).
- Telemt запущен **как бинарная systemd-служба**, **не в Docker**.
- Linux с `systemd`, `journalctl`, `python3` **3.8 или новее**.
- Права `root` или возможность выполнять команды через `sudo`.
- Исходящий HTTPS-доступ VPS к `api.telegram.org`.
- Telegram-бот с известным **токеном** и числовым **`chat_id`** получателя.
- Для установки из GitHub — `git`.

Проверьте, что MTProxyL работает:

```bash
sudo mtproxyl status
sudo mtproxyl mode --json
```

Если в сведениях о движке указано `Docker`, этот установщик не подойдёт: нужен другой источник журналов.

## Быстрая установка на VPS

### Шаг 1. Подготовьте Telegram-бота

Можно использовать **уже существующего бота MTProxyL** или создать отдельного через [@BotFather](https://t.me/BotFather) командой `/newbot`.

Вам нужны:

1. **Токен бота** — выдаётся BotFather; храните его в секрете.
2. **Числовой `chat_id`** — идентификатор приватного чата, куда будут приходить документы. В личном чате с ботом он обычно совпадает с вашим числовым Telegram ID; если используете существующий бот MTProxyL, ID его администратора можно посмотреть в настройках этого бота. Для группового чата ID другой, обычно отрицательный.

**Откройте диалог с ботом и отправьте `/start`**, прежде чем проверять доставку. Для группового чата добавьте бота в группу и убедитесь, что ему разрешено отправлять документы.

Не публикуйте токен в GitHub, скриншотах, issue или сообщениях другим людям.

### Шаг 2. Скачайте проект

Подключитесь по SSH к VPS. На Debian/Ubuntu, если `git` отсутствует:

```bash
sudo apt update
sudo apt install -y git
```

Склонируйте репозиторий:

```bash
cd ~
git clone https://github.com/vytgb76-bit/mtproxyl-logTG.git
cd mtproxyl-logTG
```

### Шаг 3. Запустите установщик

```bash
sudo bash install.sh
```

Установщик определит systemd-службу Telemt, проверит, что она запущена, и попросит:

```text
Название ЭТОГО VPS: VPS_NL
Токен Telegram-бота: [ввод скрыт]
Числовой chat_id: 123456789
```

`VPS_NL` и `123456789` здесь **только примеры**. Имя сервера должно состоять из **1–40 символов**: латинских букв, цифр, `_` или `-`.

После установки будет включён таймер `mtproxyl-logship.timer`. Telemt продолжит работать без перезапуска.

### Шаг 4. Проверьте доставку

```bash
sudo python3 /opt/mtproxyl-logship/logship.py test
```

При успешной отправке в Telegram появится документ **`VPS_NL_TEST.txt`**, а в терминале:

```text
TEST OK: Telegram confirmed the document
```

**Тест отправляет только тестовый файл**, а не накопленные логи. Для появления первого суточного архива дождитесь завершения календарного дня на VPS.

## Подключение второго и следующих серверов

Повторите **ту же установку** на каждом VPS. Используйте:

| Настройка | Первый VPS | Второй VPS | Третий VPS |
|---|---|---|---|
| Название | `VPS_NL` | `VPS_DE` | `VPS_03` |
| Токен бота | **Одинаковый** | **Одинаковый** | **Одинаковый** |
| `chat_id` | **Одинаковый** | **Одинаковый** | **Одинаковый** |

В Telegram будут приходить отдельные файлы:

```text
VPS_NL_2026-10-31.log.gz
VPS_DE_2026-10-31.log.gz
VPS_03_2026-10-31.log.gz
```

Каждый сервер работает самостоятельно. Никакого главного VPS или центральной базы данных не требуется.

## Как включить подробные логи Telemt

Сборщик **не включает подробное логирование автоматически**: эту настройку контролирует MTProxyL.

Для обычного режима Manager рекомендуется:

```bash
sudo mtproxyl tune get log_level
sudo mtproxyl tune set log_level verbose
```

Если менеджер предложит перезапустить Telemt для применения параметра, подтвердите **в удобное время**: существующие подключения могут на короткое время прерваться.

Проверить события можно через сам MTProxyL:

```bash
sudo mtproxyl logs
```

После запуска подключитесь к прокси с Telegram-клиента и посмотрите, появляются ли новые записи. Для выхода из потокового просмотра нажмите `Ctrl+C`.

**Важные уточнения:**

- При `silent` подробные события подключений могут отсутствовать.
- Конкретный состав записей зависит от версии Telemt и настроек; не гарантируется отдельная строка на каждое подключение или отключение.
- Не редактируйте напрямую генерируемый `telemt.toml` в режиме Manager — MTProxyL может перезаписать файл.
- В режиме «Супер эксперт» настройка выполняется через пользовательский конфиг Telemt; команда `tune` может быть недоступна.
- IP-адрес в журнале — не Telegram ID. Если все используют один секрет, определить конкретные аккаунты по журналу невозможно.

## Как работает расписание

Установщик создаёт systemd-таймер с `OnCalendar=hourly`.

**Это не ежечасная отправка частичных логов.** Каждый час программа проверяет, появились ли **полностью завершённые календарные дни**. Поэтому, например:

- **31 октября:** идёт накопление событий Telemt в журнале `journald`.
- **1 ноября, около 00:00:** программа экспортирует **31 октября** в `VPS_NL_2026-10-31.log.gz` и отправляет боту.
- **После подтверждения Telegram:** собственный архив и файл отслеживания отправленных частей удаляются.
- **При сетевой ошибке:** архив сохраняется и будет повторно отправлен на следующем почасовом запуске.

Если в момент полуночи VPS был выключен, `Persistent=true` позволяет запустить пропущенную проверку после включения. Отправка может быть сдвинута, если Telegram недоступен или сервер не работает.

**Часовой пояс берётся с конкретного VPS**. Проверить:

```bash
timedatectl
```

Если на разных VPS разные часовые пояса, их полночь наступит в разное время. Имя архива содержит **дату по локальному календарю соответствующего VPS**.

> [!NOTE]
> При установке отсчёт начинается с текущей локальной даты VPS. Архивы за дни **до даты установки** автоматически не создаются. Если запускать отправку вручную днём установки, неполные текущие сутки также не будут отправлены.

## Проверка и управление

### Проверить настройки без раскрытия токена

```bash
sudo python3 /opt/mtproxyl-logship/logship.py status
```

Команда показывает имя сервера, источник `journalctl`, текущую дату VPS, следующую дату для архивации и количество ожидающих архивов. **Токен бота не выводится.**

### Посмотреть расписание

```bash
systemctl list-timers --all mtproxyl-logship.timer
sudo systemctl status mtproxyl-logship.timer --no-pager
```

### Запустить проверку и отправку вручную

```bash
sudo systemctl start mtproxyl-logship.service
```

Будут обработаны только **завершившиеся дни**, которые ещё не были экспортированы; сообщения за текущие незавершённые сутки не отправляются.

### Посмотреть журнал отправщика

```bash
sudo journalctl -u mtproxyl-logship.service -n 50 --no-pager
```

Следить за новыми запусками:

```bash
sudo journalctl -u mtproxyl-logship.service -f
```

### Остановить автоматическую отправку

```bash
sudo systemctl disable --now mtproxyl-logship.timer
```

Включить обратно:

```bash
sudo systemctl enable --now mtproxyl-logship.timer
```

### Проверить файлы, ожидающие отправки

```bash
sudo ls -lh /var/lib/mtproxyl-logship/pending/
```

Не удаляйте содержимое `pending`, если там есть ещё неотправленные архивы: они нужны для повторной отправки.

## Где хранятся настройки

| Путь | Назначение |
|---|---|
| `/etc/mtproxyl-logship.json` | Имя сервера, systemd-служба Telemt, токен, `chat_id` (`0600`) |
| `/opt/mtproxyl-logship/logship.py` | Установленный отправщик |
| `/var/lib/mtproxyl-logship/cursor.json` | Дата, с которой продолжать сбор |
| `/var/lib/mtproxyl-logship/pending/` | Архивы в ожидании подтверждённой отправки |
| `/etc/systemd/system/mtproxyl-logship.service` | Одноразовый запуск отправщика |
| `/etc/systemd/system/mtproxyl-logship.timer` | Почасовое расписание с проверкой в полночь |

Для изменения имени VPS, токена бота или `chat_id` откройте конфигурацию:

```bash
sudo nano /etc/mtproxyl-logship.json
```

Пример структуры (замените значения своими):

```json
{
  "server_name": "VPS_NL",
  "unit": "mtproxyl-telemt",
  "bot_token": "123456789:REPLACE_WITH_REAL_TOKEN",
  "chat_id": "123456789"
}
```

**`unit` — только пример:** на вашем VPS имя службы может быть другим. При установке оно определяется автоматически. Не заменяйте его вслепую.

Проверить синтаксис JSON без вывода токена:

```bash
sudo python3 -c 'import json; json.load(open("/etc/mtproxyl-logship.json")); print("JSON OK")'
```

> [!CAUTION]
> Прежде чем **переименовывать** уже настроенный сервер, убедитесь, что в `pending/` нет неотправленных архивов со старым именем: отправщик выбирает ожидающие архивы по текущему имени сервера. В противном случае старые архивы могут остаться в каталоге и не отправиться автоматически.

Установщик при повторном запуске **не перезаписывает существующий** `/etc/mtproxyl-logship.json` — это защита токена и сохранённых настроек. Для изменения параметров используйте редактирование файла, а не повторную установку.

## Обновление из GitHub

Если проект уже установлен, обновить **код отправщика** можно так:

```bash
cd ~/mtproxyl-logTG
git pull --ff-only
python3 -m py_compile logship.py
sudo install -m 0700 logship.py /opt/mtproxyl-logship/logship.py
```

Новый файл будет использоваться при следующем запуске службы. **Не запускайте `install.sh` повторно** при существующей конфигурации: установщик специально прервётся, чтобы её не затереть.

> [!IMPORTANT]
> Эти команды обновляют `logship.py`, **но не переписывают уже установленные** `.service` и `.timer`. Если в будущей версии изменится способ запуска, проверьте инструкции к релизу. Перед обновлением убедитесь, что доверяете изменениям в репозитории.

## Проблемы и решения

| Симптом | Что проверить |
|---|---|
| `git: command not found` | Установите `git`: `sudo apt update && sudo apt install -y git` (Debian/Ubuntu). |
| `Не найдена установка MTProxyL` | Проверьте существование `/opt/mtproxyl/settings.conf` и то, что MTProxyL действительно установлен. |
| `Не удалось подтвердить бинарный режим` | Проверьте `sudo mtproxyl mode --json`. Для Docker текущая версия не предназначена. |
| `Не найдена служба ...` | Уточните активную службу через `sudo mtproxyl mode --json` и `systemctl`. |
| `Служба ... сейчас не работает` | Сначала восстановите работу Telemt через MTProxyL: `sudo mtproxyl status`. |
| `Telegram API: HTTP 401` | Неверный или отозванный токен бота. Исправьте конфигурацию. |
| `Telegram API: HTTP 403` | Пользователь мог заблокировать бота; откройте чат с ботом и отправьте `/start`, проверьте права. |
| `Bad Request: chat not found` | Уточните числовой `chat_id`, возможность отправки в указанный чат и то, что бот в нём присутствует. |
| Telegram недоступен, сеть оборвалась, `429` | Проверьте исходящий HTTPS и журнал отправщика. Неотправленный архив останется в очереди до следующей попытки. |
| Тест пришёл, но суточного архива нет | Возможно, ещё не наступили следующие сутки по времени VPS. Проверьте `timedatectl`, `status`, таймер и журнал службы. |
| Архив пришёл, но в нём мало событий | Проверьте уровень логирования Telemt, сам источник `mtproxyl logs` и срок хранения сообщений в `journald`. |
| После переноса MTProxyL на другое имя службы новые логи не приходят | Проверьте поле `unit` в `/etc/mtproxyl-logship.json`. |
| `Прежняя конфигурация отправки уже существует` | Это ожидаемая защита от перезаписи. Для изменения настроек редактируйте JSON; для обновления кода используйте раздел выше. |

При диагностике полезнее всего вывод **без секретов**:

```bash
sudo python3 /opt/mtproxyl-logship/logship.py status
sudo systemctl status mtproxyl-logship.timer --no-pager
sudo journalctl -u mtproxyl-logship.service -n 50 --no-pager
```

**Не публикуйте** `/etc/mtproxyl-logship.json` целиком — там находится токен бота. В самих логах могут быть IP-адреса пользователей.

## Большие архивы

Если сжатый файл превышает **45 МиБ**, отправщик разбивает его на части с названиями вида:

```text
VPS_NL_2026-10-31.log.gz.part001-of-003
VPS_NL_2026-10-31.log.gz.part002-of-003
VPS_NL_2026-10-31.log.gz.part003-of-003
```

Эти части — **фрагменты одного gzip-файла**, а не отдельные gzip-архивы. Скачайте все части в одну папку и объедините в правильном порядке (Linux):

```bash
cat VPS_NL_2026-10-31.log.gz.part* > VPS_NL_2026-10-31.log.gz
gzip -dc VPS_NL_2026-10-31.log.gz > VPS_NL_2026-10-31.log
```

Не распаковывайте каждую `.part` отдельно. Если отправлены не все части, дождитесь повторной попытки.

## Хранение и удаление логов

Потоковые логи MTProxyL в бинарном режиме читаются из **`systemd-journald`**. Программа обращается к ним через `journalctl -u <имя службы>` и сохраняет **временную сжатую копию** для отправки.

**После успешной отправки** удаляется:

- архив соответствующего дня из `/var/lib/mtproxyl-logship/pending/`;
- временный файл прогресса отправки этого архива.

**Не удаляются автоматически:**

- исходные события в `journald`;
- отдельная история трафика/IP, если её ведёт MTProxyL;
- файл конфигурации с токеном, служебный курсор и другие небольшие файлы состояния;
- данные уже отправленных сообщений в Telegram.

**Почему так:** очистка общего системного журнала способна удалить сообщения других служб и помешать диагностике. Для цели «не оставлять исходные логи на VPS» нужна **отдельная настройка источника логов и сроков хранения**, которая здесь не реализована. Сокращение хранения `journald` влияет и на остальные службы; не меняйте его без понимания последствий.

Кроме того, если `journald` удалит старые записи **до экспорта**, сборщик не сможет их восстановить. Telegram может получить файл, но отправщик не получить подтверждение — в этом редком случае возможна **повторная доставка**.

## Удаление программы

Из папки, где находится репозиторий:

```bash
cd ~/mtproxyl-logTG
sudo bash uninstall.sh
```

Скрипт удаляет systemd-таймер и службу отправщика. **MTProxyL и Telemt не затрагиваются.** Из соображений сохранности данных он **оставляет** конфигурацию, установленный файл Python и ожидающие архивы.

Если всё больше не нужно, сначала проверьте, что **в `pending/` нет важных неотправленных архивов**. Затем можно удалить оставшиеся файлы вручную:

```bash
sudo rm -f /etc/mtproxyl-logship.json
sudo rm -rf /var/lib/mtproxyl-logship
sudo rm -f /opt/mtproxyl-logship/logship.py
sudo rmdir /opt/mtproxyl-logship 2>/dev/null || true
```

**Эти команды необратимо удалят** локальную очередь, состояние и сохранённый токен приложения. На Telegram-архивы и сам прокси они не влияют.

## Безопасность и ограничения

- Журналы могут включать **IP-адреса**, время соединений и другие технические сведения. Используйте **личный чат или закрытую администраторскую группу**, контролируйте доступ и не храните эти данные дольше необходимого.
- Бот видит только то, что Telemt пишет в журнал. Он **не определяет Telegram-аккаунт** подключившегося человека.
- Токен хранится локально в `/etc/mtproxyl-logship.json` с правами `0600`. Не добавляйте этот файл в публичный репозиторий.
- Отправка работает через [Telegram Bot API](https://core.telegram.org/bots/api) и зависит от доступности Telegram и допустимого размера документов.
- Для исходного журнала важен срок хранения в `journald`; программа не обеспечивает архивирование событий, уже удалённых системой.
- При частичном сбое возможно повторное получение документа; наличие файла в чате не гарантирует бесконечное хранение на стороне Telegram.
- Поддерживается **бинарный Telemt через systemd**. Режим Docker требует адаптации.
- Один и тот же бот может получать документы от нескольких серверов независимо. Рекомендуется задавать каждому VPS **уникальное имя**.

## Проверка логики без Telegram

В репозитории есть локальные тесты. Запустить их можно так:

```bash
python3 test_logship.py
```

Они не заменяют тест отправки настоящему Telegram-боту на конкретном VPS.
