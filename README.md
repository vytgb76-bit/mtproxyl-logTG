# MTProxyL → Telegram: ежедневная отправка логов с нескольких VPS

**mtproxyl-logTG** — независимый отправщик журналов для [MTProxyL от LiafanX](https://github.com/Liafanx/MTProxyL) и движка **Telemt**. Он работает с двумя способами запуска Telemt: **Docker-контейнером** и **бинарником через systemd**.

Каждый VPS самостоятельно отправляет суточные журналы в **один Telegram-чат через одного Telegram-бота**. В названии каждого документа указывается имя сервера и дата, например:

```text
VPS_NL_2026-10-31.log.gz
VPS_DE_2026-10-31.log.gz
```

## Возможности

- **Один Telegram-бот для нескольких VPS:** на каждом сервере указываются одинаковые `bot_token` и `chat_id`, но уникальный `server_name`.
- **Docker и systemd:** источник определяется через `mtproxyl mode --json`; при недоступности команды установщик использует ограниченную проверку `/opt/mtproxyl/settings.conf`.
- **Суточные архивы:** экспортируются события завершённых суток по локальному времени соответствующего VPS; формат файла `.log.gz`.
- **Автоматическая доставка:** `systemd.timer` запускает отправщик в начале каждого часа, включая полночь; в первую проверку после полуночи отправляется вчерашний журнал.
- **Повтор после ошибок:** если Telegram недоступен, файл остаётся в очереди до успешной передачи. После подтверждения API удаляется только временный архив отправщика.
- **Тестовая отправка:** `logship.py test` отправляет небольшой документ без клиентских логов и помогает проверить токен и чат.
- **Крупные документы:** файлы больше **45 МиБ** разбиваются на части; передача возобновляется с ещё не подтверждённой части.
- **Без входящих портов:** исходящее HTTPS-соединение к `api.telegram.org` и метод Bot API `sendDocument`.
- **Без вмешательства в MTProxyL:** скрипты установки и отправки **не меняют** транспорт, порты, секреты, правила MEKO/Zapret, режим движка и не перезапускают Telemt.

Схема:

```text
VPS_NL ── MTProxyL / Telemt (бинарник) ── journalctl ──┐
                                                      ├──> один бот ──> приватный чат
VPS_DE ── MTProxyL / Telemt (Docker) ── docker logs ───┘       
                  |                                         
           независимые таймеры                   архивы с именем VPS и датой
```

> [!NOTE]
> Это **не второй бот-процесс**, принимающий команды Telegram. Отправщик только вызывает `sendDocument` и не делает запросов `getUpdates`, поэтому может использовать токен уже работающего бота MTProxyL, не конкурируя с ним за входящие сообщения. Telegram хранит документы в чате; это не отдельная база данных бота.

## Требования

- Рабочий **MTProxyL с Telemt** в режиме `manager`; автопроверка ориентируется на `mtproxyl mode --json` и наличие `/opt/mtproxyl/settings.conf`.
- Linux с **systemd**, Python **3.8+** и правами `root` (обычно через `sudo`).
- Для **Docker**: запущенный контейнер, установленный `docker` CLI и доступность его журналов через `docker logs`. Драйвер логов должен поддерживать чтение `docker logs`.
- Для **бинарного Telemt**: запущенная systemd-служба и работающая команда `journalctl`.
- Исходящий HTTPS-доступ VPS к `api.telegram.org` (TCP 443). Входящий порт для отправщика не требуется.
- Telegram-бот (новый или существующий), его **токен** и **числовой идентификатор чата (`chat_id`)**.
- `git` для установки и обновления из GitHub.

Проверка MTProxyL без изменения настроек:

```bash
sudo mtproxyl mode --json
```

Примеры полей:

```json
{
  "engine": "docker",
  "log_kind": "docker",
  "log_target": "mtproxyl",
  "running": true
}
```

```json
{
  "engine": "binary",
  "log_kind": "service",
  "log_target": "mtproxyl-telemt",
  "running": true
}
```

Это **примеры сокращённого ответа**, не полный вывод MTProxyL. Имя службы может отличаться от приведённого. Установщик пытается определить реальное имя автоматически.

## Различия Docker и бинарного режима

| Параметр | Бинарный Telemt | Docker Telemt |
|---|---|---|
| Как MTProxyL показывает источник | `log_kind: service` | `log_kind: docker` |
| Как читает отправщик | `journalctl -u <служба>` | `docker logs <контейнер>` |
| Где исходные события | `systemd-journald` | Журналы контейнера, управляемые Docker |
| Что должно работать | systemd-служба | Контейнер и `docker logs` |
| Где может потеряться история | очистка/ротация journald | ротация или удаление журналов Docker, пересоздание контейнера |

Встречавшиеся конфигурации:

- **MTProxyL v1.6.11 + Telemt v3.5.5:** движок-бинарник, журнал службы.
- **MTProxyL v1.7.17 + Telemt v3.4.25:** Docker-контейнер `mtproxyl`.

Версия самого MTProxyL **не является надёжным признаком режима**: проверяйте фактические поля `engine`, `log_kind`, `log_target` и `running`, а не номер версии.

Проверка журналов вручную (только чтение):

```bash
# Docker: если имя контейнера действительно mtproxyl
sudo docker logs --tail 30 mtproxyl

# Бинарник: замените имя на фактическое log_target
sudo journalctl -u mtproxyl-telemt -n 30 --no-pager
```

Настройки Docker-логирования можно посмотреть **без изменения**:

```bash
sudo docker inspect --format '{{json .HostConfig.LogConfig}}' mtproxyl
```

Если Docker удалит записи **до** ночной выгрузки, отправщик восстановить их не сможет. Отправщик выгружает логи завершённого дня и не ведёт непрерывную копию событий в отдельном файле.

## Быстрая установка на VPS

### Шаг 1. Подготовьте Telegram-бота

Можно использовать **уже существующего бота MTProxyL** или создать отдельного с помощью [@BotFather](https://t.me/BotFather) (`/newbot`). Нужны:

1. **Токен** вида `123456789:ABC...` — секрет, выдаваемый BotFather.
2. **Числовой `chat_id`** — адресат документов. Для личного чата это ваш ID, для группы обычно отрицательное число.

**Откройте чат с выбранным ботом и отправьте `/start`**, затем убедитесь, что бот может писать в этот чат. Если используется закрытая группа, добавьте бота и дайте ему право отправлять документы.

Если уже настроен Telegram-бот MTProxyL, `chat_id` администратора часто известен из настроек этого бота. Не путайте `chat_id` с `@username` или токеном. Не публикуйте токен в README, GitHub Issues, скриншотах или сообщениях.

### Шаг 2. Скачайте проект на VPS

Подключитесь к серверу по SSH. Если `git` отсутствует (Debian/Ubuntu):

```bash
sudo apt update
sudo apt install -y git
```

Загрузите исходники:

```bash
cd ~
git clone https://github.com/vytgb76-bit/mtproxyl-logTG.git
cd mtproxyl-logTG
```

**Если каталог уже есть**, второй раз клонировать не нужно:

```bash
cd ~/mtproxyl-logTG
git pull --ff-only
```

> [!IMPORTANT]
> Перед установкой на Docker-VPS убедитесь, что в репозитории уже размещены **обновлённые `install.sh` и `logship.py`** из пакета с поддержкой Docker. Старые версии поддерживали только бинарный движок. Обновление одного README ошибку установки не исправит.

### Шаг 3. Установите отправщик

```bash
sudo bash install.sh
```

Установщик прочитает сведения о режиме MTProxyL, проверит источник логов и спросит:

```text
Имя ЭТОГО VPS (латиница, цифры, _ и -, например VPS_DE): VPS_DE
Токен Telegram-бота (общий для всех VPS): [ввод скрыт]
Числовой chat_id (общий для всех VPS): 123456789
```

Здесь `VPS_DE` и `123456789` — **примеры**. Имя: от 1 до 40 символов, латинские буквы, цифры, `_`, `-`.

При обнаружении Docker должен появиться примерно такой вывод:

```text
Источник обнаружен: Docker-контейнер mtproxyl
```

А при бинарном движке — имя реально работающей systemd-службы. Затем создаются файл настроек, рабочий каталог и таймер отправщика. **Telemt и MTProxyL установщик не перезапускает**.

Если установщик увидит существующий `/etc/mtproxyl-logship.json`, он остановится — это защита от перезаписи уже настроенного отправщика. Для изменения настроек используйте раздел [«Где хранятся настройки»](#где-хранятся-настройки), для обновления — [«Обновление из GitHub»](#обновление-из-github).

### Шаг 4. Проверьте Telegram, не дожидаясь полуночи

```bash
sudo python3 /opt/mtproxyl-logship/logship.py test
```

Если всё успешно, в чате появится файл `VPS_DE_TEST.txt`, а на VPS:

```text
TEST OK: Telegram confirmed the document
```

Это **только тестовый текстовый файл**, не журнал пользователей. Проверка подтверждает связь с Telegram, но не доказывает, что Telemt уже пишет подробные события. Как включить нужный уровень и проверить журнал, см. ниже.

### Шаг 5. Проверьте таймер

```bash
sudo python3 /opt/mtproxyl-logship/logship.py status
systemctl list-timers --all mtproxyl-logship.timer
sudo systemctl status mtproxyl-logship.timer --no-pager
```

Ожидайте первый суточный архив **после завершения дня установки по времени VPS**. Для немедленной обработки уже завершённых дней можно использовать `sudo systemctl start mtproxyl-logship.service`; текущий неполный день эта команда не отправит.

## Подключение второго и следующих серверов

На каждом VPS устанавливается **собственная копия отправщика**; общий «главный сервер» не требуется. Параметры:

| Параметр | Первый VPS | Второй VPS | Третий VPS |
|---|---|---|---|
| `server_name` | `VPS_NL` | `VPS_DE` | `VPS_03` |
| `bot_token` | Один и тот же | Один и тот же | Один и тот же |
| `chat_id` | Один и тот же | Один и тот же | Один и тот же |
| Движок Telemt | Может быть бинарник | Может быть Docker | Любой поддерживаемый |

Файлы в Telegram не перепутаются:

```text
VPS_NL_2026-10-31.log.gz
VPS_DE_2026-10-31.log.gz
VPS_03_2026-10-31.log.gz
```

**Сценарий двух VPS:**

1. На VPS с бинарным движком и уже работающим отправщиком **ничего переустанавливать не требуется**.
2. В GitHub обновите **оба** файла `install.sh` и `logship.py` до версии с поддержкой Docker, а также замените README.
3. На Docker-VPS выполните `cd ~/mtproxyl-logTG && git pull --ff-only && sudo bash install.sh`.
4. Укажите **новое имя сервера**, но тот же `bot_token` и `chat_id`, что на первом VPS.
5. Запустите `test` и проверьте, что документ пришёл с именем второго сервера.

Одинаковый токен бота можно использовать одновременно: отправщик выполняет только исходящие запросы `sendDocument`. Он не запускает ещё одного обработчика сообщений бота. Если у серверов разные часовые пояса, архивы придут в разные моменты их локальной полуночи.

## Как включить подробные логи Telemt

Программа отправляет **то, что реально записывает Telemt в свой журнал**, а не вычисляет IP или подключения самостоятельно. Если подробные события не включены, суточный архив может содержать только сообщения запуска и ошибки.

Для обычного режима MTProxyL Manager сначала посмотрите текущий уровень:

```bash
sudo mtproxyl tune get log_level
```

При необходимости включите `verbose`:

```bash
sudo mtproxyl tune set log_level verbose
```

MTProxyL может предложить **перезапуск Telemt**. Если подтверждаете, существующие подключения на короткое время прервутся. **Отправщик логов самостоятельно Telemt не перезапускает.**

После применения откройте журналы командой MTProxyL:

```bash
sudo mtproxyl logs
```

Либо напрямую по выбранному режиму:

```bash
# Docker
sudo docker logs --tail 50 mtproxyl

# Бинарник — укажите фактическое имя службы из mode --json
sudo journalctl -u mtproxyl-telemt -n 50 --no-pager
```

Подключите Telegram-клиент к прокси и посмотрите, появляются ли события; для выхода из потокового просмотра используйте `Ctrl+C`.

> [!CAUTION]
> В обычном режиме Manager **не редактируйте напрямую** генерируемый Telemt TOML-конфиг: MTProxyL может его перезаписать. В режиме «Супер эксперт» настройка может управляться пользовательским конфигом, и команда `tune` может быть недоступна.

**Что означают записи:** IP в журнале — адрес сетевого соединения, не Telegram ID. Название пользователя/секрета может относиться к записи MTProxyL, но не обязательно обозначает человека. Одно устройство может создавать несколько соединений. Наличие записи `handshake` зависит от версии движка и выбранного уровня логирования.

## Как работает расписание

Установщик создаёт `mtproxyl-logship.timer` с `OnCalendar=hourly` и `AccuracySec=1s`. Таймер запускает **проверку в начале каждого часа**, включая около **00:00 по часовому поясу VPS**. Это не значит, что логи каждый час отправляются частями: экспортируются только **полностью завершившиеся календарные сутки**.

Пример:

- **31 октября:** Telemt пишет события в системный журнал или журнал Docker.
- **1 ноября, около 00:00:** отправщик экспортирует 31 октября, создаёт `VPS_NL_2026-10-31.log.gz` и отправляет его в Telegram.
- **После подтверждения `sendDocument`:** удаляет архив из своей локальной очереди.
- **Если отправка не удалась:** оставляет архив и повторяет попытку каждый час.
- **Если VPS был выключен:** `Persistent=true` запускает пропущенную проверку после включения при доступности журнала.

Проверить часы и часовой пояс:

```bash
timedatectl
```

Часовой пояс может различаться между VPS; дата в имени файла определяется **по локальному календарю конкретного сервера**. Времени для доставки может потребоваться больше нескольких секунд из-за объёма данных или сети.

**Начальная дата:** при установке отправщик сохраняет текущую дату VPS и не экспортирует автоматически исторические дни **до установки**. Проверка `test` не меняет эту дату. Команда `run` или ручной запуск службы выгружает лишь дни, которые уже завершились. За один запуск обрабатывается не более **31 дня** отложенной архивации, остальное продолжится на следующих запусках.

Если исходный системный или Docker-журнал был очищен/перезаписан **до ночной выгрузки**, архив уже не сможет содержать утраченные события. Это особенно важно при большом объёме verbose-логов.

## Проверка и управление

### Узнать выбранный источник и очередь (без токена)

```bash
sudo python3 /opt/mtproxyl-logship/logship.py status
```

Будут показаны имя VPS, `Source: docker logs ...` либо `Source: journalctl -u ...`, дата VPS, следующая дата архивации и число ожидающих файлов. **Токен не показывается.** Это проверка настроек отправщика, а не гарантированная проверка доступности исходного журнала.

### Проверить отправку боту

```bash
sudo python3 /opt/mtproxyl-logship/logship.py test
```

В чате должен появиться `ИМЯ_СЕРВЕРА_TEST.txt`. Тест не архивирует текущий день и не отправляет пользовательские журналы.

### Проверить расписание

```bash
systemctl list-timers --all mtproxyl-logship.timer
sudo systemctl status mtproxyl-logship.timer --no-pager
```

### Вручную запустить сбор и повторную отправку

```bash
sudo systemctl start mtproxyl-logship.service
```

**Важно:** будут обработаны только завершённые даты, начиная с даты установки. Текущий неполный день не выгружается досрочно.

### Смотреть ошибки самого отправщика

```bash
sudo journalctl -u mtproxyl-logship.service -n 60 --no-pager
```

Для наблюдения в реальном времени:

```bash
sudo journalctl -u mtproxyl-logship.service -f
```

### Посмотреть ожидающие файлы

```bash
sudo ls -lah /var/lib/mtproxyl-logship/pending/
```

Архив `.log.gz` может находиться там, если Telegram недоступен. Рядом может быть `.progress.json`, который отмечает уже подтверждённые части. **Не удаляйте очередь**, пока не убедитесь, что нужные документы успешно получены в Telegram.

### Временно остановить отправку

```bash
sudo systemctl disable --now mtproxyl-logship.timer
```

Включить заново:

```bash
sudo systemctl enable --now mtproxyl-logship.timer
```

Это не останавливает прокси и не меняет собственные журналы Telemt.

## Где хранятся настройки

| Путь | Назначение |
|---|---|
| `/etc/mtproxyl-logship.json` | Имя VPS, тип источника, имя контейнера/службы, токен, `chat_id`; права `0600` |
| `/opt/mtproxyl-logship/logship.py` | Установленная копия отправщика |
| `/var/lib/mtproxyl-logship/cursor.json` | Дата следующего экспорта (`next_date`) |
| `/var/lib/mtproxyl-logship/pending/` | Суточные архивы и прогресс отправки |
| `/var/lib/mtproxyl-logship/lock` | Защита от одновременного запуска двух экземпляров |
| `/etc/systemd/system/mtproxyl-logship.service` | Одноразовый запуск Python-отправщика |
| `/etc/systemd/system/mtproxyl-logship.timer` | Почасовая проверка и отправка |

В новой версии источник хранится в полях `source_kind` и `source_target`.

Пример **для Docker** (значения токена и чата вымышленные):

```json
{
  "server_name": "VPS_DE",
  "source_kind": "docker",
  "source_target": "mtproxyl",
  "bot_token": "123456789:PUT_YOUR_TOKEN_HERE",
  "chat_id": "123456789"
}
```

Пример **для бинарника**:

```json
{
  "server_name": "VPS_NL",
  "source_kind": "service",
  "source_target": "mtproxyl-telemt",
  "bot_token": "123456789:PUT_YOUR_TOKEN_HERE",
  "chat_id": "123456789"
}
```

`source_target` должен быть **фактическим именем контейнера или службы** на этом сервере. Не копируйте пример без проверки `sudo mtproxyl mode --json`.

**Совместимость:** старая конфигурация первого VPS с ключом `"unit"` поддерживается новым `logship.py` — она автоматически трактуется как `source_kind: service`. Для уже работающего первого VPS обновление не обязательно.

При изменении имени сервера, токена или чата:

```bash
sudo nano /etc/mtproxyl-logship.json
```

После сохранения проверьте JSON, не показывая содержимое:

```bash
sudo python3 -c 'import json; json.load(open("/etc/mtproxyl-logship.json")); print("JSON OK")'
```

И выполните `test`. **Повторно запускать `install.sh` при существующей конфигурации не нужно**: установщик прервётся, чтобы не перезаписать её.

> [!CAUTION]
> Если меняете `server_name` на сервере с уже накопленной очередью, сначала убедитесь, что в `pending/` нет архивов со старым именем. Отправщик выбирает ожидающие файлы по текущему имени сервера; старые могут перестать выбираться автоматически.
>
> При переносе MTProxyL с Docker на бинарник (или обратно) обновите **оба поля** `source_kind` и `source_target`, иначе будет читаться старый источник. Сам режим Telemt ради отправки менять не требуется.

**Не публикуйте файл настроек целиком:** в нём находится действующий токен бота. Права конфигурации устанавливаются как `0600`, однако `root` на VPS имеет к ней доступ.

## Обновление из GitHub

### 1. Обновить файлы репозитория

```bash
cd ~/mtproxyl-logTG
git pull --ff-only
```

Если Git сообщает о локальных изменениях, сначала разберитесь с ними; принудительно сбрасывать локальные файлы без резервной копии не нужно.

### 2. Если отправщик уже установлен — обновить рабочую копию Python

```bash
cd ~/mtproxyl-logTG
python3 -m py_compile logship.py
sudo install -m 0700 logship.py /opt/mtproxyl-logship/logship.py
```

На **уже работающем первом VPS** это необязательный шаг. Установщик положил копию Python-скрипта в `/opt/mtproxyl-logship/`, и обновления GitHub сами по себе не влияют на работающую установку.

После обновления кода (при необходимости) можно проверить:

```bash
sudo python3 /opt/mtproxyl-logship/logship.py status
sudo python3 /opt/mtproxyl-logship/logship.py test
```

**Не запускайте `install.sh` повторно** поверх существующего `/etc/mtproxyl-logship.json` — он специально отказывается перезаписывать настройки. Команды выше обновляют только код Python, **но не переписывают** файлы `.service`/`.timer`. Если будущий выпуск меняет systemd-настройки, нужны отдельные инструкции миграции.

### 3. Что нужно обновить на GitHub для Docker

Если в репозитории до сих пор старая версия, загрузите **в одном обновлении**:

- `install.sh` — определяет Docker или systemd;
- `logship.py` — читает Docker или journalctl и создаёт архивы;
- `README.md` — этот подробный документ;
- `test_logship.py` — локальные проверки двух режимов.

Один только `README.md` не исправляет ошибку «Не удалось подтвердить бинарный режим». `uninstall.sh` из исправленного комплекта сохраняет настройки и очередь, как и предыдущая версия.

## Проблемы и решения

| Ошибка или симптом | Причина / действие |
|---|---|
| `git: command not found` | Установите `git`: `sudo apt update && sudo apt install -y git` (Debian/Ubuntu). |
| `Не удалось подтвердить бинарный режим` | На VPS, вероятно, **Docker**, а `install.sh` ещё старой версии. Обновите `install.sh` **и** `logship.py` на GitHub, затем `git pull --ff-only`. |
| `Не найдена установка MTProxyL` | Установщик ждёт `/opt/mtproxyl/settings.conf`. Проверьте расположение MTProxyL и `sudo mtproxyl mode --json`. |
| `Неизвестный ENGINE_BACKEND` / неподдерживаемый `log_kind` | Посмотрите `sudo mtproxyl mode --json`; приложение принимает `docker` или `service`. Другой режим автоматически не поддерживается. |
| `running=false` | MTProxyL сообщает, что прокси не запущен. Сначала проверьте работу самого движка через MTProxyL. |
| `Docker не найден в PATH` | Проверьте `docker --version` и запущенный Docker. Установщик не устанавливает Docker и не меняет режим прокси. |
| `Не удалось найти Docker-контейнер` | Проверьте точное `log_target` из `sudo mtproxyl mode --json` и список контейнеров: `sudo docker ps --all`. |
| `Docker не смог прочитать логи контейнера` | Проверьте `sudo docker logs --tail 20 mtproxyl`, драйвер логирования, права и состояние контейнера. |
| `Служба ... неактивна или не найдена` | При бинарном движке проверьте имя `log_target` и `systemctl status <имя>.service`. |
| `Telegram API: HTTP 401` | Токен бота неверный или отозван. Обновите его в `/etc/mtproxyl-logship.json`. |
| `Telegram API: HTTP 403` | Бот мог быть заблокирован пользователем или лишён доступа. Откройте чат, отправьте `/start`, проверьте права. |
| `Bad Request: chat not found` | Неверный `chat_id`, бот не находится в нужной группе или у него нет доступа. |
| `429 Too Many Requests` | Ограничение Bot API. Архив остаётся в очереди и повторится на следующем запуске. |
| `Telegram API: ...`, сеть недоступна | Проверьте DNS, исходящий HTTPS и `sudo journalctl -u mtproxyl-logship.service -n 60 --no-pager`. |
| `Настройки отправщика уже существуют` | Это штатная защита от перезаписи. Для изменения редактируйте JSON; для обновления кода используйте раздел выше. |
| `test` работает, но архивов нет | Проверьте `timedatectl`, `status`, таймер и дату установки: незавершённый день не экспортируется. |
| Архив пустой или в нём мало строк | Проверьте источник (`docker logs`/`journalctl`), уровень `log_level`, ротацию исходных журналов и время работы контейнера. |
| Архив за один день пришёл дважды | В редком случае Telegram принял документ, а ответ не дошёл; повторная отправка возможна. |
| Docker-контейнер пересоздали | Старые журналы могут быть утрачены; проверьте источник и срок хранения Docker. |
| Источник MTProxyL переименовался после установки | Проверьте `/etc/mtproxyl-logship.json` и обновите `source_target` по текущему `mode --json`. |
| В `pending/` есть старые файлы после смены имени VPS | Отправщик выбирает очередь по текущему `server_name`. Верните имя до отправки очереди или обработайте старые файлы отдельно. |

Команды, с которыми удобно разбирать проблему (не включают показ токена):

```bash
sudo mtproxyl mode --json
sudo python3 /opt/mtproxyl-logship/logship.py status
sudo systemctl status mtproxyl-logship.timer --no-pager
sudo journalctl -u mtproxyl-logship.service -n 60 --no-pager
```

В командах и журналах **могут встречаться IP-адреса и другие чувствительные данные** — перед публикацией удалите их. **Не показывайте файл `/etc/mtproxyl-logship.json` или действующий токен.**

## Большие архивы

Если сжатый файл превышает **45 МиБ**, отправщик разбивает его на части с названиями вида:

```text
VPS_NL_2026-10-31.log.gz.part001-of-003
VPS_NL_2026-10-31.log.gz.part002-of-003
VPS_NL_2026-10-31.log.gz.part003-of-003
```

Эти части — **фрагменты одного gzip-файла**, а не отдельные gzip-архивы. Скачайте все части в одну папку и объедините в правильном порядке (Linux):

```bash
cat VPS_NL_2026-10-31.log.gz.part* > VPS_NL_2026-10-31.log.gz
gzip -dc VPS_NL_2026-10-31.log.gz > VPS_NL_2026-10-31.log
```

Не распаковывайте каждую `.part` отдельно. Если отправлены не все части, дождитесь повторной попытки.

## Хранение и удаление логов

**Как устроена текущая версия:** программа не подменяет стандартное логирование Telemt. В конце суток она читает накопившийся журнал **из `systemd-journald` или Docker**, формирует временную сжатую копию, отправляет её в Telegram и после подтверждения удаляет **только копию**.

### Что удаляется после успешной отправки

- Файл `ИМЯ_VPS_ГГГГ-ММ-ДД.log.gz` из `/var/lib/mtproxyl-logship/pending/`.
- Файл прогресса `.progress.json` для данного архива.

### Что не удаляется

- **Исходные события** Telemt в `journald` или в Docker-логах. Их срок хранения определяется настройками соответствующей системы.
- Отдельная статистика/IP-история, которую может хранить сам MTProxyL.
- Файл конфигурации с токеном и служебный `cursor.json`.
- Уже доставленные документы в Telegram-чате.

**Следствие:** требование «логи хранятся только в Telegram, а на VPS их совсем нет» текущая архитектура **не выполняет**. Она сокращает время хранения **собственных архивов** на VPS, но не управляет источником записей. Агрессивная очистка общего `journald` может повредить диагностике других служб, а принудительное удаление Docker-журналов повлиять на работу MTProxyL. Поэтому проект намеренно не делает глобальную очистку.

**Неполнота архива:** Docker/journald могут очистить или ротировать исходный журнал до ночного экспорта. Тогда утраченные строки не будут восстановлены. Избыточно маленький лимит журналов и подробное `verbose` увеличивают этот риск.

**Редкий дубль:** если Telegram получил файл, а отправщик не получил подтверждение, при повторной попытке он может прислать тот же документ повторно. Это лучше, чем безвозвратно удалить неподтверждённый архив.

### Что на самом деле хранится в Telegram

Документы сохраняются **в переписке с ботом или в указанной группе**, а не на виртуальном диске внутри самого бота. Важные архивы при необходимости дополнительно сохраняйте в надёжном месте; доступность файлов зависит от работы Telegram и доступа к этому чату.

## Удаление программы

Из папки с исходниками:

```bash
cd ~/mtproxyl-logTG
sudo bash uninstall.sh
```

Скрипт отключает и удаляет `mtproxyl-logship.timer` и `.service`, затем выполняет `systemctl daemon-reload`. **MTProxyL, Telemt, Docker-контейнер и исходные логи не трогает**.

В целях защиты от потери данных сохраняются:

- `/etc/mtproxyl-logship.json` (включает токен бота);
- `/var/lib/mtproxyl-logship/` (очередь архивов, дата экспорта);
- `/opt/mtproxyl-logship/logship.py` (установленная копия Python).

Если уверены, что очередь не нужна, можно **вручную** удалить остатки:

```bash
sudo rm -f /etc/mtproxyl-logship.json
sudo rm -rf /var/lib/mtproxyl-logship
sudo rm -f /opt/mtproxyl-logship/logship.py
sudo rmdir /opt/mtproxyl-logship 2>/dev/null || true
```

> [!WARNING]
> Это необратимо уничтожит локальную очередь, состояние отправщика и сохранённый токен. Сначала убедитесь, что все нужные документы доставлены в Telegram. Эти команды **не удаляют исходные журналы Docker/journald**.

## Безопасность и ограничения

- **Токен бота — секрет.** Установщик принимает его без отображения на экране и сохраняет в `/etc/mtproxyl-logship.json` с правами `0600`. Не загружайте этот файл на GitHub, не добавляйте в Issues и не публикуйте в чатах.
- **Логи могут содержать IP-адреса** клиентов, время соединений, имена секретов, технические ошибки и сведения о сетевой активности. Используйте личный чат или закрытую администраторскую группу, ограничьте доступ и соблюдайте применимые требования к хранению таких данных.
- **Telegram-аккаунты пользователей не определяются.** Сетевая запись `peer=...` и имя секрета не раскрывают, кто является владельцем конкретного Telegram-аккаунта; число соединений не равно числу людей.
- **Никаких новых входящих портов не требуется.** Отправщик инициирует только исходящее HTTPS-соединение к Telegram Bot API.
- **Не гарантируется доставка строго в 00:00:00.** Таймер запускает проверку около границы часа; реальная отправка зависит от состояния VPS, объёма логов и сети.
- **Удаляются только временные копии.** Docker и `journald` продолжают хранить оригиналы по собственной политике, а в MTProxyL может существовать независимая статистика.
- **Контроль полноты зависит от исходных журналов.** Перезапуск, пересоздание контейнера, ротация и очистка могут удалить события до выгрузки.
- **Доставка не строго exactly-once.** Сетевые сбои могут вызвать повторную отправку; при невозможности отправить документ он остаётся в очереди.
- **Изменение режима движка** после установки требует проверки `source_kind`/`source_target` в настройках отправщика.
- **Совместимость:** требуется MTProxyL, возвращающий поддерживаемый `log_kind` (или подходящий `settings.conf`), и Telemt, который действительно пишет нужные события.

## Проверка логики без Telegram

Проверка Python-скрипта без соединения с Telegram или настоящим прокси:

```bash
python3 test_logship.py
```

Тесты охватывают экспорт из `journalctl`, формирование Docker-команды, обработку ошибок источника, совместимость старой конфигурации первого VPS и сохранение неотправленного архива при сетевом сбое. Локальные тесты **не подтверждают**, что на конкретном VPS включены нужные логи и бот может получать документы. Для этого используйте `logship.py test`, `status` и просмотр журналов.

## Частые вопросы

**Можно ли один и тот же бот использовать на десяти VPS?**  
Да. Для каждого VPS задайте уникальный `server_name`, но используйте общий токен и `chat_id`. Отправщик не принимает входящие команды бота, а только отправляет документы.

**Можно ли использовать встроенного Telegram-бота MTProxyL?**  
Да, если известен его токен и нужный `chat_id`. Отправщик использует `sendDocument` и не обращается к `getUpdates`.

**Первый VPS уже работает. Надо ли его обновлять при добавлении Docker на втором?**  
Нет. Он использует установленную копию Python-скрипта. Обновить первый VPS можно позже, если есть потребность и согласованы изменения.

**Почему установка на втором VPS раньше сообщала «Не удалось подтвердить бинарный режим»?**  
Потому что в прежнем `install.sh` допускался только бинарный Telemt, а на втором VPS `mtproxyl mode --json` возвращает `"engine":"docker"`, `"log_kind":"docker"` и `"log_target":"mtproxyl"`. Для такого источника нужны исправленные `install.sh` **и** `logship.py`.

**Бот прислал тестовый файл. Значит ли это, что всё готово?**  
Доставка в чат работает, но стоит отдельно проверить, что Telemt пишет нужные события, а таймер включён. Нужный журнал может быть пустым при `silent`.

**Почему лог не приходит сразу после установки?**  
При установке счёт начинается с текущей даты. Суточный архив появится только после завершения этого дня; `test` отправляет только тестовый документ.

**Что произойдёт, если Telegram выключится или VPS потеряет связь?**  
Неподтверждённый архив останется в очереди и будет повторно отправляться при следующих почасовых запусках. Возможны дубликаты при неоднозначном сетевом подтверждении.

**Могу ли я удалять архивы с VPS сразу после отправки?**  
Отправщик уже делает это со **своими временными архивами**. Исходный журнал Docker/journald он не очищает; это отдельная задача, и изменение политики хранения может нарушить другие функции сервера.

**Можно ли изменить время отправки с полуночи?**  
Да, но это требует согласованного изменения расписания и логики экспорта календарных суток. Простая замена `OnCalendar` влияет на момент запуска, а не на дату, которую экспортирует скрипт. Для стандартного варианта ничего менять не нужно.
